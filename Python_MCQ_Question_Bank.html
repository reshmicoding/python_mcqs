Q1. This exact confusion appears in the Lab 1 notebook. Suppose the following is saved as audit.py and run from the command line with python audit.py (NOT typed into a Jupyter cell):

"""
This script automates financial audit processes.
"""
print("Audit started")
  1. A. Two lines print: the docstring text, then "Audit started".
  2. B. Only "Audit started" is printed.
  3. C. Nothing is printed, because triple-quoted text is a comment that Python skips entirely, including the print() call.

Show Answer

Correct answer: B

The triple-quoted block is not a comment — Python has no multi-line comment syntax. It is a string literal used as a standalone expression statement. In a script, unused expression results are never displayed (that only happens in the interactive REPL/Jupyter, which echoes the value of the last expression as Out[]). So only the explicit print("Audit started") produces visible output.

Why the others are wrong:

  • A confuses REPL/notebook echo behavior with script execution — in Jupyter this string would show as Out[], but running as a .py file never echoes bare expressions.
  • C incorrectly treats the triple-quoted string as a real comment; Python still parses and evaluates it as code, it just produces no visible side effect.
  • D is wrong because triple-quoted strings are valid, fully legal multi-line string literals — there is no syntax error.

Concept: docstrings/string literals vs. comments; REPL echo vs. script execution

Correct answer: C

Q1. From PDA's reference-semantics example:

a = [1, 2, 3]
b = a
a.append(4)
print(b)
  1. A. [1, 2, 3] — b is unaffected
  2. B. [1, 2, 3, 4] — b reflects the change
  3. C. An error, because b was never explicitly reassigned
  4. D. [4] — only the appended element
Show Answer

Correct answer: B

b = a does not copy the list — it makes b a second name referring to the very same list object as a. a.append(4) mutates that one underlying object in place, so viewing it through either name shows the update.

Why the others are wrong:

  • A assumes assignment copies the list, as it would in some other languages — Python assignment only binds names to objects.
  • C is wrong; no reassignment of b is needed since b and a already point to the same mutable object.
  • D misunderstands append as replacing the list rather than adding to it.

Concept: assignment as reference binding, not copying

True or False

Q2. Continuing the same scenario: c = list(a). True or False: a is c evaluates to True.

  1. A. True
  2. B. False
Show Answer

Correct answer: B (False)

list(a) always constructs a brand-new list object containing copies of the references inside a. So while a == c is True (equal contents), a is c is False because they are two distinct objects in memory.

Why the other is wrong:

  • A confuses value equality (==) with object identity (is) — a very common beginner mix-up that PDA calls out explicitly.

Concept: is (identity) vs. == (equality); the list() constructor as a copy operation

Q3. A colleague writes a helper function inspired by PDA's append_element example:

def append_item(item, target_list=[]):
    target_list.append(item)
    return target_list

result1 = append_item("apple")
result2 = append_item("banana")
print(result1)
print(result2)
  1. A. ['apple'] then ['banana'] — each call gets a fresh empty list
  2. B. ['apple', 'banana'] printed twice — both calls share the same default list
  3. C. TypeError, because default arguments cannot be lists
  4. D. ['apple'] then ['apple', 'banana']
Show Answer

Correct answer: B

Default argument values are evaluated once, when the def statement executes — not once per call. So target_list=[] creates a single list object that becomes permanently bound to the function's default and is reused (and mutated) on every call that doesn't supply its own list. After append_item("apple"), that shared list is ['apple']; after append_item("banana"), it becomes ['apple', 'banana'] — and both result1 and result2 point at that same object, so printing either shows the fully accumulated list.

Why the others are wrong:

  • A is the intuitive-but-wrong assumption most learners make — it would be true only if the default were re-created fresh each call (which is how it works for, e.g., a default of None handled inside the function body).
  • C is wrong; lists are perfectly legal default values syntactically — the danger is semantic (shared mutable state), not a syntax error.
  • D incorrectly shows result1 as if it "froze" at the time of its own call — but result1 and result2 are literally the same object, so printing result1 *after* result2 was populated shows the same accumulated contents.

Concept: the mutable default argument pitfall

Correct answer: B

  2. B. Prints "ab" with no error at all — type hints are not enforced at runtime
  3. C. Prints 0
  4. D. Raises a SyntaxError because of the -> int annotation
Show Answer

Correct answer: B

Python's type annotations (x: int, -> int) are purely informational/documentation — intended for human readers and external static type checkers (like mypy) to analyze *before* the program runs. The Python interpreter itself completely ignores them at runtime and performs no type checking or enforcement whatsoever. Since + is defined for two strings (concatenation), calling total("a", "b") runs the function body exactly as written and simply returns "a" + "b", i.e. "ab", despite blatantly violating the annotated types.

Why the others are wrong: A is the very common, incorrect assumption that annotations behave like a statically-typed language's enforced type system; C is not a plausible result of string concatenation; D is wrong — this annotation syntax is fully valid and executes without any parsing issue.

Concept: Python type hints are unenforced at runtime (documentation for humans/static checkers only)
